Zabbix 日常巡检与维护窗口管理

用数据、问题、容量与自身健康四条线做日常巡检，并规范维护窗口的创建。

2026年10月21日 5 分钟阅读 运维手册 Zabbix监控巡检 监控与告警

一句话定位

巡检不是把界面点一遍，而是用固定的几条线判断监控体系本身是否健康：数据在不在、问题有没有闭环、容量还能不能撑住、变更前有没有留下维护窗口。这篇指南把日常动作和窗口管理固化成一条可交接的路径。

适用场景

  • 值班交接班或每日例行检查，需要判断平台是否可用。
  • 计划变更前后创建维护窗口，避免批量告警淹没真实故障。
  • 故障复盘时翻历史问题与指标曲线，还原时间线。
  • 新同事接手监控平台，需要一条标准的上手路径。
  • 告警收件人调整、值班表轮换后的通知链路核对。

前置条件

项目要求
账号巡检用只读账号，写操作走变更账号
权限账号可见主机组覆盖本人负责的业务范围
时间浏览器、服务端与被监控主机时区一致
通知告警收件人列表与电话升级名单为最新版本
变更维护窗口的范围、起止时间与责任人已确认

操作步骤

1. 每日巡检四条线

先跑固定四项，任何一项异常再往下钻。四条线覆盖了数据链路、问题队列、容量趋势和平台自身健康，比逐个页面翻看更快发现系统性问题。

巡检项看什么判定
数据链路最新数据是否刷新、采集间隔是否正常超过两个采集周期无值即异常
问题队列未关闭问题数量与最老问题时长存在长期未闭环的严重问题即异常
容量趋势监控项数、每秒新增值、队列长度、缓存占用连续三天上涨即需评估
平台自身服务端与代理进程、数据库空间、日志报错出现错误日志即跟进

2. 查看监控数据与图形

最新数据页面按主机组过滤，能看到每个监控项最近一次取值与刷新时间；点开监控项后的图形可以看单个指标曲线；图形与仪表盘页面适合把常用性能指标拼在一起看。日常关注的是「值有没有变」和「间隔稳不稳」，不必逐项核对数值。

也可以用接口批量拉取，避免手工翻页：

# 拉取当前未关闭问题（地址与令牌为占位符）
curl -s -X POST 'https://zabbix.example.com/api_jsonrpc.php' \
  -H 'Content-Type: application/json-rpc' \
  -d '{"jsonrpc":"2.0","method":"problem.get","params":{"output":"extend","recent":true,"sortfield":"eventid","sortorder":"DESC"},"auth":"<api-token>","id":1}'

3. 问题查询与闭环

历史问题在问题页面切换「历史记录」，按主机组、严重程度和时间范围筛选，适合复盘；要快速定位某个问题项的走势，直接点该问题进入历史记录，选定时间周期即可。处理完一轮后把结论写回变更记录或值班日志，做到每一条严重问题都有责任人和处理时间。

4. 创建维护窗口

变更开始前在「配置 — 维护 — 创建维护期间」新建一条记录。名称写清系统与事由；维护类型选「无数据收集」；启用时间比真实操作窗口提前一点开始、延后一点结束，避免操作前几分钟和收尾阶段的抖动触发告警；周期选一次性，长度覆盖整个操作；范围在主机组和主机之间二选一，不要同时填。

# 创建一次性维护窗口（参数与令牌为占位符）
curl -s -X POST 'https://zabbix.example.com/api_jsonrpc.php' \
  -H 'Content-Type: application/json-rpc' \
  -d '{
    "jsonrpc": "2.0",
    "method": "maintenance.create",
    "params": {
      "name": "业务系统变更维护",
      "maintenance_type": 1,
      "active_since": 1790000000,
      "active_till": 1790003600,
      "groupids": ["2"],
      "timeperiods": [{"timeperiod_type": 0, "start_date": 1790000000, "period": 3600}]
    },
    "auth": "<api-token>",
    "id": 1
  }'

维护类型为「无数据收集」时，窗口内不采集数据也不计算触发器，适合停机割接；如果只是重启单机、期望继续采集，应选带数据收集的类型。

5. 调整通知对象

在用户的通知配置里，邮箱一般覆盖一般严重与严重级别，电话只覆盖严重与灾难级别，避免所有告警都走语音。调整前确认值班表，调整后发一条测试通知确认链路通。

6. 维护仪表盘

按业务系统建仪表盘，放上核心资源曲线、未关闭问题列表、代理心跳与队列趋势。仪表盘的价值在交接和应急时一眼看清全局，条目不宜过多，三到五块足够。

7. 数据库与日志维护

历史数据保留周期要和容量匹配，常规指标保留 30 到 90 天即可，趋势数据可以更长。每周看一次数据库表空间与慢查询，日志按大小轮转，避免单个文件把分区占满。清理历史数据要走接口或平台自带工具，不要直接删表，否则容易把配置和索引一起破坏。

验证

  • 维护窗口生效期间该范围内不再产生新问题，窗口结束后告警恢复。
  • 接口返回的问题列表与界面一致，严重级别计数可核对。
  • 测试通知能到达收件人，升级链路中每个节点都收到。
  • 巡检记录已落表，异常项标注了跟进人和处理时间。

风险与回滚

维护窗口范围过大的直接后果是真实故障被静默，窗口本身变成盲区，因此范围必须精确到本次变更涉及的主机组或主机。窗口的起止时间要核对时区和跨天，跨零点时容易少填一天。误建窗口时直接停用或删除该维护期间即可恢复，但已进入窗口的告警不会补发，需要在窗口结束后人工确认一遍相关主机。

通知对象调整会影响整条升级链路，改动前留存原配置，改完立即发测试消息。历史维护记录建议停用而不删除，留作复盘依据。

常见问题

维护期间仍然收到告警。 维护只抑制窗口内新产生的事件，窗口开始前已存在的问题不会消失；也请检查主机是否真的落在维护范围内。

窗口结束后问题立刻恢复。 属于正常现象，触发器会重新计算一次；若长时间不恢复，再去看数据是否回来。

历史问题查不到。 多半是主机组或时间范围过滤过窄，也可能是数据保留周期已经过去。

仪表盘打开很慢。 图表时间范围过大或聚合项过多，缩短范围、减少图表数量即可。
