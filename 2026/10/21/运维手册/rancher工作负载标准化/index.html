Rancher 工作负载标准化配置

把工作负载的资源配置、健康检查、调度分散与对外暴露固定成一套标准动作。

2026年10月21日 6 分钟阅读 运维手册 RancherKubernetes工作负载 容器与云原生

一句话定位

把 Rancher 里创建一个业务工作负载必须做的几件事固定成标准顺序：资源预留与上限、健康检查、调度分散、存储挂载、对外暴露，谁来做都得到同一套参数。

适用场景

  • 新业务首次在项目命名空间里创建工作负载。
  • 存量工作负载迁移或重建，需要补齐资源规格与健康检查。
  • 平台巡检发现部分工作负载没设上限、没配探针，按标准整改。
  • 测试、预发、生产多套环境需要复用同一份参数模板。

前置条件

  • Rancher 管理端可用，目标集群状态为 Active。
  • 目标项目与命名空间已创建，执行账号在该命名空间具备工作负载编辑权限。
  • 业务镜像已推送到私有仓库 registry-a.example.com，节点能正常拉取。
  • 研发已确认监听端口、健康检查路径、CPU 与内存规格；这三项拿不到就先别建。
  • 需要对外暴露的服务，域名与证书已就绪，解析指向集群入口地址。
  • 已确认工作负载是长驻服务还是定时任务，控制器类型不同，探针与反亲和的落法也不同。

概念与原理

Rancher 的「工作负载」是 Kubernetes 控制器的一层表单封装，表单背后仍是 Deployment、DaemonSet、StatefulSet 这类原生对象，落地后可以直接用 kubectl 核对，不必只在界面上点。

资源要分成两个值看。预留值决定调度器把 Pod 摆到哪台节点：节点剩余可分配资源必须覆盖预留值，否则 Pod 一直停在 Pending。上限值决定容器最多能用多少，超出后被内核终止并重启，事件里能看到 OOMKilled。只写上限不写预留，节点会被超卖；只写预留不写上限，单个容器能把整机内存吃干净。

健康检查由三个探针分担不同职责。启动探针只判断进程有没有起来，启动慢的服务要给它足够的失败次数，否则会被误杀；就绪探针决定要不要放流量，探测不过时端点被摘掉但容器不重启；存活探针负责发现假死并重启。三组参数分开设，不要用一套数字套所有服务。

配探针本质是用响应时间换稳定性。探测有间隔，从故障发生到容器被重启之间必然存在一段不可用窗口，阈值宁可留出余量，也不要卡着秒级去压，否则业务高峰期的正常抖动会被判成故障。

调度分散靠标签加反亲和实现。先给工作负载打业务标签，再用反亲和要求同标签副本不要挤在同一台节点；副本数大于节点数时用软约束更稳妥。

参数不要只留在界面里。每份工作负载的标准参数要同步进台账或配置仓库，重建时直接套模板，比对着截图回忆可靠得多。

存储与暴露放在最后。有落盘需求先建 PVC，再通过数据卷挂进容器；对外访问分两层，集群内用 Service，集群外用 Ingress 接域名与证书。

操作步骤

  1. 建命名空间并落下工作负载骨架。先不带探针和 Ingress，确认镜像能正常起。界面创建与 YAML 提交等价，团队统一走 YAML，方便评审与回溯。
kubectl create namespace namespace-demo
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-app
  namespace: namespace-demo
  labels:
    app.kubernetes.io/name: demo-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app.kubernetes.io/name: demo-app
  template:
    metadata:
      labels:
        app.kubernetes.io/name: demo-app
    spec:
      containers:
        - name: app
          image: registry-a.example.com/app/demo:1.0.0
          ports:
            - containerPort: 8080
  1. 补资源预留与上限。按压测结果给；没有压测数据时，先按观察到的峰值加三成留余量。下面的片段追加到上面容器的 spec 里。
          resources:
            requests:
              cpu: 500m
              memory: 512Mi
            limits:
              cpu: "1"
              memory: 1Gi

常见类型的起步值可参考下表，上线后按实际用量回调。

服务类型预留 CPU预留内存上限 CPU上限内存
轻量接口服务200m256Mi1512Mi
常规业务服务500m512Mi22Gi
计算密集型11Gi44Gi
  1. 配三类探针。启动探针放宽，存活与就绪收紧，探测路径由研发提供，不要用根路径糊弄。
          startupProbe:
            httpGet:
              path: /healthz
              port: 8080
            failureThreshold: 30
            periodSeconds: 5
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 3
            failureThreshold: 3
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8080
            periodSeconds: 20
            timeoutSeconds: 3
            failureThreshold: 3
  1. 打业务标签并配置反亲和，让三个副本尽量分散到不同节点。
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                topologyKey: kubernetes.io/hostname
                labelSelector:
                  matchLabels:
                    app.kubernetes.io/name: demo-app
  1. 有落盘需求时先建 PVC，再用数据卷挂载。存储类选平台已提供的，不要临时拿 hostPath 顶替。
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: demo-data
  namespace: namespace-demo
spec:
  accessModes: ["ReadWriteOnce"]
  storageClassName: local-path
  resources:
    requests:
      storage: 20Gi

挂载部分写成：

          volumeMounts:
            - name: data
              mountPath: /data
      volumes:
        - name: data
          persistentVolumeClaim:
            claimName: demo-data
  1. 暴露服务。集群内先建 Service，对外再建 Ingress。域名提前解析好，证书交给平台统一的证书方案处理，不在工作负载里各配一套。
apiVersion: v1
kind: Service
metadata:
  name: demo-app
  namespace: namespace-demo
spec:
  selector:
    app.kubernetes.io/name: demo-app
  ports:
    - port: 80
      targetPort: 8080
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: demo-app
  namespace: namespace-demo
spec:
  ingressClassName: nginx
  rules:
    - host: demo.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: demo-app
                port:
                  number: 80
  1. 提交并观察滚动发布。副本逐个替换，只有就绪探针通过的才接流量。
kubectl apply -f demo-app.yaml
kubectl rollout status deployment/demo-app -n namespace-demo

验证

kubectl get pods -n namespace-demo -o wide
kubectl describe pod -n namespace-demo -l app.kubernetes.io/name=demo-app | grep -A5 Limits
kubectl top pod -n namespace-demo
curl -s -o /dev/null -w "%{http_code}\n" http://demo.example.com/ready
kubectl get ingress -n namespace-demo
  • 三个 Pod 落在不同节点，说明反亲和生效。
  • Pod 的 Limits 与 Requests 齐全，与台账一致。
  • 探针事件持续成功，没有反复重启记录。
  • 域名返回 200，说明 Service 到 Ingress 的链路通。
  • 用 describe 看节点分配与资源占用，和规划值对得上。
  • 把参数与台账核对一次，避免界面上改完忘了同步。

风险与回滚

  • 上限设太低会 OOMKilled，表现为发布后不断重启；把上一版参数改回来即可恢复。
  • 预留设太高会 Pending，节点明明有空闲却调度不上，按实际用量下调。
  • 探针超时太短，业务高峰期稍慢就被重启，容易连成雪崩，先放宽阈值再观察。
  • 就绪探针写错路径会让端点永远不 Ready，流量进不来；先在集群内 curl 验证路径。
  • 硬反亲和（required）在节点不足时直接调度失败，生产环境建议用软约束。
  • Ingress 改动立即生效，会影响线上域名。改前留一份旧 YAML，回滚用 kubectl rollout undo 或重新 apply 旧文件。
  • PVC 的回收策略若是 Delete，删 PVC 会连带删数据，动手前先确认已有备份。

现象常见原因处理思路
Pod 长期 Pending预留值超过节点可分配资源下调 requests 或扩节点
