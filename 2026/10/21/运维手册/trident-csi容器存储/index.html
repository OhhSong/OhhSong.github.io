Trident CSI 容器存储接入手册

把企业级 NAS 存储接入 Kubernetes 的完整流程，含 CSI 驱动安装、后端配置与存储类验证。

2026年10月21日 5 分钟阅读 运维手册 TridentCSI存储Kubernetes 容器与云原生

一句话定位

Trident 是企业级 NAS 存储在 Kubernetes 上的 CSI 驱动：以容器方式跑在集群里，把卷的创建、挂载、扩容、快照这些动作交给集群自己完成，业务侧只需要提交一个 PVC。

适用场景

  • 新集群要接集中式 NAS 存储，希望 PV 能按 PVC 自动供给，而不是逐个手工建卷。
  • 业务需要多 Pod 同时读写的共享目录，NFS 形态比块设备更合适。
  • 希望存储的申请与回收由 K8s 管理员在集群内闭环，不再每次走存储管理员工单。
  • 老业务上容器平台，要求复用现网已有的 NAS 存储池和既有备份、快照体系。

前置条件

  • 集群版本在驱动支持矩阵内。计划升级 Kubernetes 时先升级驱动，再升集群，顺序反了会卡在中间状态。
  • 存储侧已建好 SVM，划好 aggregate，创建供集群访问的 NFS LIF，导出策略允许节点网段以读写方式访问。
  • 管理网与业务网互不相通时，要为 SVM 单独配一个业务网段的管理地址，否则驱动连不上存储管理接口，后端一直加不上。
  • 一套可用的内网镜像仓库，能把安装清单里列出的镜像全部推进去；纯内网环境这一步无法跳过。
  • 各节点装好 NFS 客户端工具，节点到存储的 RPC 与 NFS 端口放通。

架构与原理

  • 控制器：以 Deployment 形式运行，接收 CSI 请求，调用存储管理接口创建或删除卷，并维护后端配置。
  • 节点组件：以 DaemonSet 形式运行，每个节点一个 Pod，负责把卷挂到节点上并暴露给容器。
  • 配置对象：后端、卷、快照等都以 CRD 形式保存在集群中，kubectl get tridentbackends 这类查询是可信来源，排查时优先看它。
  • StorageClass 通过 provisioner 名称和 backendType 两个信息，把 PVC 路由到某个后端；PVC 只写容量和存储类名，其余细节由驱动补齐。

卷的生命周期完全由集群侧驱动：PVC 提交后控制器调存储接口建卷，卷名与 PVC 的标识一一对应；扩容走 allowVolumeExpansion，改大 PVC 容量后由驱动去扩后端卷；删除则取决于回收策略。所以排障时按「PVC → PV → 驱动卷记录 → 存储侧卷名」这条链路逐段对照，能很快判断断在哪一环。

操作步骤

  1. 存储侧准备。SVM、aggregate、NFS LIF、导出策略四件事按厂商文档做完，导出策略至少要允许集群节点网段读写：
# 示意：命令以存储厂商 CLI 为准，参数中的地址与名称均为占位符
net int create -vserver <svm> -lif svm-nfs-lif -service-policy default-data-files \
  -address 192.0.2.21 -netmask <netmask> -home-node <node> -home-port <port>
export-policy rule create -policyname default -clientmatch 192.0.2.0/24 \
  -rorule any -rwrule any
  1. 下载并解压安装包：
tar -zxvf trident-installer-<version>.tar.gz
cd trident-installer
./tridentctl -n trident install --help
  1. 生成安装清单并把镜像地址改成内网仓库：
mkdir -p ~/trident-work && cd ~/trident-work
/path/to/trident-installer/tridentctl -n trident install \
  --image-registry registry-a.example.com/trident \
  --silence-autosupport \
  --generate-custom-yaml
grep -i "image:" setup/*.yaml | sort -u

把列出的镜像逐个同步到内网仓库后，从现成清单安装：

/path/to/trident-installer/tridentctl -n trident install --use-custom-yaml
  1. 确认组件已跑起来：
kubectl -n trident get pods
kubectl get csidrivers
./tridentctl -n trident version
  1. 建后端凭证对象。账号口令放集群对象里，不要写进后端配置文件：
apiVersion: v1
kind: Secret
metadata:
  name: nas-backend-auth
  namespace: trident
type: Opaque
stringData:
  # 键名与格式按驱动文档要求，值从企业凭据系统取用，勿写入仓库
  credential: "<REDACTED>"
  1. 写后端配置并提交。managementLIF 填业务网段的管理地址，凭证引用上一步的对象，导出策略交给驱动自动维护：
{
  "version": 1,
  "storageDriverName": "<vendor-nas-driver>",
  "backendName": "nas-backend-01",
  "managementLIF": "192.0.2.20",
  "nfsMountOptions": "nfsvers=3",
  "credentials": { "name": "nas-backend-auth" },
  "autoExportPolicy": true,
  "autoExportCIDRs": ["192.0.2.0/24"],
  "defaults": {
    "spaceReserve": "none",
    "snapshotPolicy": "none",
    "snapshotReserve": "0",
    "unixPermissions": "777",
    "securityStyle": "unix"
  }
}
./tridentctl -n trident create backend -f backend.json
./tridentctl -n trident get backend -o yaml

storageDriverName 与 StorageClass 里的 backendType 必须取同一个值，取值以驱动文档为准，不要自己猜。

  1. 创建 StorageClass。provisioner 名称先用 kubectl get csidrivers 查出来再填：
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: nas-sc
provisioner: csi.trident.<vendor-domain>
parameters:
  backendType: "<vendor-nas-driver>"
  provisioningType: "thin"
  snapshots: "true"
  clones: "true"
reclaimPolicy: Retain
allowVolumeExpansion: true
kubectl apply -f sc.yaml
kubectl get sc nas-sc -o yaml
  1. 用一个测试 PVC 打通全链路，读写模式按后端能力选 ReadWriteMany：
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: nas-test-pvc
  namespace: namespace-demo
spec:
  accessModes: ["ReadWriteMany"]
  storageClassName: nas-sc
  resources:
    requests:
      storage: 10Gi
kubectl -n namespace-demo apply -f pvc.yaml
kubectl -n namespace-demo get pvc nas-test-pvc -w

PVC 变为 Bound 后挂进一个 Pod 写文件，再从另一个 Pod 读回来，确认共享读写正常。

验证

  • kubectl -n trident get pods 中控制器与节点组件全部 Running，节点组件的数量等于节点数。
  • tridentctl get backend 状态为 success，能看到关联的 aggregate 与可用容量。
  • kubectl get pv 里新 PV 的 StorageClass 与实际使用的一致，容量与 PVC 申请值相符。
  • 存储侧按卷名能查到对应 flexvol，说明驱动确实调到了存储。
  • 快照与克隆按需验证：创建快照后再克隆一个卷，确认数据一致。

风险与回滚

  • 回收策略是最大的坑：reclaimPolicy 为 Delete 时，删除 PVC 会连存储卷一起删掉。生产一律先用 Retain，清理动作由人来做。
  • 后端配置文件里的口令在创建成功后已加密存入集群对象，本地文件应清空或妥善保管，别留在跳板机的公共目录。
  • 版本顺序：先升驱动再升 Kubernetes。驱动卸载与重装期间，已有 PV 的挂载会中断，需在维护窗口做。
  • 卸载驱动：
./tridentctl -n trident uninstall
kubectl get crd | grep trident

注意卸载会清理驱动自己的 CRD，但存储侧的卷和数据仍然保留，删除 CRD 前确认没有 PVC 依赖。

  • 快照与克隆功能依赖存储许可与存储系统版本，能力不具备时先把 StorageClass 里对应开关关掉，避免业务侧误用。

常见问题

现象常见原因处理思路
PVC 一直 PendingStorageClass 的 backendType 与后端不匹配，或后端未就绪对齐两处取值，tridentctl get backend 看状态
建后端时报连接失败managementLIF 不通、网段不通、端口被拦从节点上直接探测管理地址与端口
Pod 挂载失败提示权限不足导出策略没放行节点网段调整导出规则，核对 autoExportCIDRs
删除 PVC 后存储侧卷还在回收策略是 Retain确认数据不再需要后手工删卷
tridentctl 查询不到资源kubeconfig 或命名空间不对指定正确 context 与 -n trident
节点组件数量少于节点数DaemonSet 有节点未调度看是否被污点挡住、镜像是否拉取成功
