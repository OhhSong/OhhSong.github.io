宿主机双网卡 bond 绑定配置

容器宿主机业务口与存储口双网卡聚合的配置流程，含前置清理、模式选型、验证与回滚。

2026年10月21日 5 分钟阅读 运维手册 Linux网络Bonding高可用 网络与传输

一句话定位

把两块以上物理网卡聚合成一个逻辑接口，让宿主机同时获得带宽叠加、流量分担和单链路故障时的自动切换能力——这就是双网卡绑定要解决的问题。

适用场景

  • 容器宿主机需要同时跑业务流量与存储流量，两条链路各自独立成组。
  • 关键节点服务器、高网络 IO 的服务器，单网线或单交换机端口故障不能导致整机失联。
  • 网络共享存储服务器，带宽需求超过单块网卡上限。
  • 承接搬迁机、挪用机，机器上残留了旧的绑定配置，需要清干净再重建。

前置条件

  • 至少两块同速率的物理网卡，且都已被系统识别、状态为 UP。
  • 交换机侧已按选定的模式完成配置。LACP 模式必须先在交换机上建好聚合口，两边模式不一致时链路起不来。
  • 有带外管理或本地终端。改网络配置过程中 SSH 随时可能断，纯远程操作风险很高。
  • 规划好两套网段：业务口一套，存储口一套，不要混用，也不要给两块聚合口配同一个网段。
  • root 权限，且 NetworkManager 服务可用。

绑定模式怎么选

模式特点交换机侧要求
lacp 动态链路聚合按 802.3ad 协商，成员口共享同一速率，带宽可叠加，单口故障自动摘除需支持 802.3ad 并建聚合口
activebackup 主备同一时刻只有主口转发，主口故障后切到备口，提供冗余但不叠加带宽无需交换机特殊配置
roundrobin 轮询按顺序轮流发包，提供负载与容错，乱序风险相对高需建聚合口
loadbalance 负载均衡按源目地址或 MAC 计算选路，分担流量需建聚合口
broadcast 广播容错每个报文从所有成员口各发一份，容错最强、浪费带宽需建聚合口

生产环境的宿主机优先选 lacp：带宽能叠加，单口故障只降速不断网。只有在交换机不支持 802.3ad、或者两块网卡分属不同交换机且无法做跨设备聚合时，才退回 activebackup。

另外注意发行版差异：早期 RHEL 6 时代统一用 bond，RHEL 7/8 官方推荐 team，更新的发行版和 NetworkManager 对 bonding 的支持又更完整。具体用 team 还是 bond，按实际发行版文档选，本文以 team 为例，操作思路对 bond 同样适用。

前置清理

这一步最容易被跳过，但残留的配置会让新绑定行为诡异，一定要先查干净。

  1. 查看当前的接口与地址，区分物理网卡和虚拟网卡：
ip a

状态为 DOWN 且没有地址的虚拟接口，基本都是上次配置留下的残渣，逐个删除。

  1. 查看现有的连接与绑定策略：
nmcli connection show

除物理网卡之外的历史绑定策略，确认不在用后全部删除。

  1. 检查配置文件目录：
ls -l /etc/sysconfig/network-scripts/

残留的 ifcfg 文件里保存着旧设备的绑定参数，不在用的直接删掉，避免和新建的配置打架。

操作步骤

  1. 创建业务口聚合接口。示例用 lacp 模式，接口名 team0，两块物理口 ens1f0、ens2f0 作为成员：
nmcli connection add type team con-name team0 ifname team0 \
  config '{"runner":{"name":"lacp"}}'
  1. 把成员口挂到聚合接口下：
nmcli connection add type team-slave con-name team0-p1 ifname ens1f0 master team0
nmcli connection add type team-slave con-name team0-p2 ifname ens2f0 master team0
  1. 先把手动模式打开，再写地址。顺序反了，部分 NetworkManager 版本会报错：
nmcli connection modify team0 ipv4.method manual
nmcli connection modify team0 \
  ipv4.addresses 192.0.2.10/24 \
  ipv4.gateway 192.0.2.1 \
  ipv4.dns 192.0.2.53
  1. 启用接口：
nmcli connection up team0-p1
nmcli connection up team0-p2
nmcli connection up team0
  1. 存储口按同样步骤建第二组聚合接口，用另一对物理口，配另一段地址，且不要配网关（一台机器只留一个默认网关，多网关会导致回包路径混乱）：
nmcli connection add type team con-name team1 ifname team1 \
  config '{"runner":{"name":"lacp"}}'
nmcli connection add type team-slave con-name team1-p1 ifname ens1f1 master team1
nmcli connection add type team-slave con-name team1-p2 ifname ens2f1 master team1
nmcli connection modify team1 ipv4.method manual
nmcli connection modify team1 ipv4.addresses 192.0.2.20/24
nmcli connection up team1
  1. 固化启动参数。查到生成的 ifcfg 文件，把引导协议改成静态：
grep BOOTPROTO /etc/sysconfig/network-scripts/ifcfg-team0
# 把 none 改为 static，保证重启后不会重新获取地址

如果是手工维护 ifcfg，记得地址、掩码、网关三处都写全，只写地址不写掩码同样会出问题。

验证

ip a show team0
teamdctl team0 state
nmcli connection show team0
ping -I team0 -c 4 192.0.2.1
  • teamdctl 输出里 runner 应为 lacp，两个成员的 link 状态都是 up。
  • ip a 中聚合接口为 UP，地址与规划一致，业务口与存储口分属不同网段。
  • 用 ip route 确认只有一条默认路由，指向业务网关。
  • 收敛验证：在业务低峰期拔掉其中一根网线，观察 ping 丢包数量，预期只丢一两个包即恢复；再把网线插回，确认端口自动恢复 up。
  • 重启一次机器，复查接口地址、路由与运行模式，确认配置持久化生效。

风险与回滚

  • 最大的风险是操作中断网失联。务必在带外或本地终端执行，并提前把回滚命令准备好。
  • LACP 与交换机配置不一致时，链路会一直协商不上，表现为接口 UP 但不通。先确认交换机侧聚合口模式与成员端口，再查主机侧。
  • 同一聚合组内成员口的速率、双工、MTU 必须一致，否则部分流量会异常。
  • 回滚方式，删除新建的连接与接口并恢复原有配置：
nmcli connection down team0
nmcli connection delete team0 team0-p1 team0-p2
ip a
  • BOOTPROTO 没改成 static 是重启后地址漂移的常见原因，改完一定复查该参数。

常见问题

现象常见原因处理思路
聚合接口起不来成员口被别的连接占用，或残留旧绑定清理旧连接与 ifcfg 文件后重建
接口 UP 但不通lacp 与交换机模式不匹配核对交换机聚合口配置，或临时改 activebackup 验证
teamdctl 显示成员 degraded单根网线、光模块或交换机端口故障更换线缆或端口，检查光功率
重启后配置丢失BOOTPROTO 非 static，或 NetworkManager 未托管该接口改静态配置，确认接口在托管列表内
只有一条链路有流量模式为 activebackup，或负载哈希只命中一个口属正常现象，按模式特性理解，必要时调整哈希策略
两块口配了同一网段规划错误业务与存储分网段，重新分配地址
