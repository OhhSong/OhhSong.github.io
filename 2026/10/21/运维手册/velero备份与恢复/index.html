Velero 容器备份与恢复实践

Kubernetes 集群 Velero 备份恢复的落地手册，覆盖部署、定时备份、跨集群恢复与回滚演练。

2026年10月21日 6 分钟阅读 运维手册 VeleroKubernetes备份 容器与云原生

一句话定位

Velero 回答的是「Kubernetes 里的东西丢了怎么找回来」：把集群中的资源对象（Deployment、Service、ConfigMap、Secret、PVC 等）以及工作负载的持久卷数据归档到集群外的对象存储，需要时再拉回原集群或另一套集群。

适用场景

  • 某个命名空间被误删，对应的 YAML 又没进版本库，需要按命名空间粒度找回。
  • 平台组件升级、CRD 变更、存储替换之前留一个保护点，出问题能退回升级前的状态。
  • 生产与容灾两套集群指向同一个存储桶，容灾侧按需取回数据。
  • 新建集群或机房搬迁，把工作负载整体复制到另一套环境。
  • 有合规要求，需要按固定周期保留一份可读的备份。

它和 etcd 快照不是一回事，也不该互相替代：etcd 快照把 API 对象整包拿走，恢复速度快，适合整集群不可用的极端情况，但它不包含 PV 里的业务数据；Velero 覆盖资源加数据，代价是恢复时必须有一个活着的集群。生产上通常是二者并存，集群证书、kubeadm 配置文件、etcd 快照都要单独纳入备份清单。

前置条件

  • 确认 Velero 版本与 Kubernetes 版本兼容；打算升级 Kubernetes 时，先确认 Velero 已支持目标版本，别倒过来做。
  • 一个 S3 兼容的对象存储桶（提前创建），以及仅对该桶有读写权限的专用账号。
  • 一台能访问 API Server 的运维机，装好 kubectl 与 velero 命令行；要管多套集群就把各自的 kubeconfig 都放进去。
  • 备份窗口内业务能接受短暂的 IO 抖动，具体程度取决于卷的备份方式。
  • 记录当前集群的 StorageClass 清单——跨集群恢复时两边必须同名，否则卷挂不上。

架构与实现要点

服务端：以 Deployment 形式部署在集群内的独立命名空间，附带控制器，负责监听自定义资源并执行实际动作；节点侧另有 DaemonSet 组件读取卷数据（新版本称 node-agent，旧版本是 restic 守护进程，两者只能选其一）。

客户端：运维机上的 velero 命令本身不传数据，只是把意图写成自定义资源提交给 API Server，再回来读取执行结果。

一次备份的链路是：命令提交 Backup 对象 → 控制器监听到并开始采集 → 从 API Server 读取资源清单 → 资源清单与卷数据分头上传到对象存储 → 状态回写。备份、定时计划、恢复各自对应一种自定义资源，记录保存在 etcd 中。

对象存储是唯一数据源：控制器会持续比对桶内数据与集群内记录，桶里找不到对应数据时，集群内的备份记录也会被一并清理。这个设计带来的直接后果是——桶被误删，备份记录会跟着消失。所以生产环境通常会再叠一层存储侧的跨站点同步或版本控制作为兜底。

部署步骤

  1. 在运维机上准备好两套集群的访问方式：
export KUBECONFIG=$HOME/.kube/cluster-a.yaml:$HOME/.kube/cluster-b.yaml
kubectl config get-contexts
kubectl config use-context cluster-a

把 export 写进 ~/.bashrc，避免每次登录重配。

  1. 创建命名空间：
kubectl create namespace velero-system

  1. 准备对象存储凭证。用只授权该桶的专用账号，把密钥对写成两行键值格式的文本文件，权限改成 600，放在运维机的受控目录；不要提交进代码仓库，也不要贴到工单或聊天里。

  2. 安装服务端，以生产集群 A 为例：

velero install \
  --provider aws \
  --plugins velero/velero-plugin-for-aws:v1.10.0 \
  --namespace velero-system \
  --bucket <your-bucket> \
  --use-volume-snapshots=true \
  --default-volumes-to-fs-backup \
  --backup-location-config region=us-east-1,s3ForcePathStyle=true,s3Url=http://192.0.2.30:8084

命令末尾还需要追加一个凭据文件参数，把上一步的文件注册成集群内的凭证对象。该参数在不同小版本上名称不完全统一，执行前先跑 velero install --help 核对，不要凭记忆写。

  1. 容灾集群 B 用同一条命令再装一次，只把 s3Url 换成 B 侧可访问的存储入口地址，桶名保持完全一致。两边指向同一个桶，B 集群自然能看到 A 集群产生的备份。

  2. 关键参数备查：

参数作用说明
—provider声明存储插件类型S3 兼容对象存储统一填 aws
—bucket存放备份的桶需提前创建，两套集群同名
—use-volume-snapshots是否创建卷快照对象后端具备 CSI 快照能力时设 true
—default-volumes-to-fs-backup卷数据走文件级备份旧版本对应 restic 相关参数，注意版本差异
—backup-location-config桶的访问配置region、s3ForcePathStyle、s3Url 三项即可

备份操作

按命名空间做一次性备份：

velero backup create namespace-demo-$(date +%Y%m%d%H%M) \
  --include-namespaces namespace-demo \
  --default-volumes-to-fs-backup \
  -n velero-system

排除掉 Velero 自身与其它系统命名空间，做一次全集群备份：

velero backup create all-ns-backup \
  --exclude-namespaces velero-system,namespace-demo \
  --snapshot-volumes=false

定时任务，每天凌晨 1 点执行、保留 72 小时：

velero schedule create daily-ns \
  --schedule="0 1 * * *" \
  --ttl 72h \
  --include-namespaces namespace-demo

定时任务产生的备份名为「计划名-时间戳」，恢复时按完整名字指定。

常用筛选参数：

参数含义
—include-resources只备份指定资源类型，例如 deployments
—exclude-resources跳过指定资源类型
—selector按标签挑对象，例如 app=web
—include-cluster-resources是否包含集群级资源，可取 true / false / 不填
—ttl保留时长，不写默认 30 天

批量备份可以按命名空间循环，把每个命名空间的输出分别重定向到日志文件，避免某个命名空间失败后静默跳过。

恢复操作

先说必须先记住的一条：恢复只会创建集群里不存在的对象，已存在的同名资源不会被覆盖，也不会退回旧版本。真要回滚，得先删掉现有资源再执行恢复，删除动作不可撤销。

按备份点恢复指定命名空间：

velero restore create \
  --from-backup namespace-demo-20261021081500 \
  --include-namespaces namespace-demo

改名字恢复，避免与现有环境冲突：

velero restore create \
  --from-backup namespace-demo-20261021081500 \
  --namespace-mappings namespace-demo:namespace-demo-restore

在容灾集群侧恢复，前提是已建好同名 StorageClass，否则 PVC 会一直 Pending：

velero restore create --from-backup namespace-demo-20261021081500 --restore-volumes

验证

kubectl get pods -n velero-system
velero backup-location get -n velero-system
velero backup get -n velero-system
velero backup describe <backup-name> --details
velero backup logs <backup-name>
  • 存储位置状态应为 Available；不是的话，先排查桶入口地址、凭证权限和网络可达性。
  • 备份 Phase 为 Completed 才算完成；PartiallyFailed 要展开看是哪些资源或卷失败，不能只看总量。
  • 定期做恢复演练：拉一套测试命名空间，从最近的备份恢复出来，比对对象数量和 PVC 挂载情况。没有演练过的备份，只能算心理安慰。

风险与回滚

  • 桶是单点：对象存储被误删，备份记录会跟着消失。建议在存储侧开启版本控制或跨站点复制。
  • 恢复不覆盖：回滚前先删现有资源，务必反复确认目标命名空间，别在生产上删错。
  • 跨云迁移限制：不同云厂商之间持久卷没法直接搬，只能在新环境重建存储并单独同步数据。
  • TTL 到期自动清理：重要保护点把 TTL 设长一些，或额外保留一份副本。
  • 个别资源不想被备份，直接打排除标签：
kubectl label namespace/namespace-demo velero.io/exclude-from-backup=true

卸载（只清 Velero 自己的自定义资源，桶里的数据保留）：

kubectl delete namespace/velero-system
kubectl delete clusterrolebinding/velero-velero-system
kubectl delete crds -l component=velero

常见问题

现象常见原因处理思路
存储位置不可用桶地址不可达、region 不符、凭证无权限在运维机上探测入口地址，核对桶策略与凭证
备份长时间 InProgress卷数据量大、节点组件未就绪看 backup logs，确认 node-agent 是否 Running
卷数据没备下来未开文件级备份，或用了 HostPath补开卷备份参数；HostPath 需换支持的卷类型
恢复后 PVC 一直 Pending目标集群缺同名 StorageClass 或后端容量不足先建 StorageClass，再确认存储侧可用容量
定时任务没按时触发时区理解偏差、旧记录被 TTL 清掉核对控制器时区与 —ttl 设置
