K8s 集群新增节点初始化清单

存量集群扩容时的节点初始化步骤，覆盖 DNS 固化、域名解析、镜像仓库与纳管接入。

2026年1月30日 6 分钟阅读 运维手册 Kubernetes集群运维节点初始化 容器与云原生

一句话定位

这是一份存量 Kubernetes 集群扩容新节点时的初始化清单：从裸机交付到节点可被纳管、可正常拉镜像、可加入集群，中间该做什么、顺序是什么、怎么验证。

适用场景

  • 业务扩容，给已有集群加 worker 节点。
  • 节点硬件故障后换新机补位。
  • 机房搬迁或资源池调整，一批机器重新接入。
  • 集群要接入统一的集群纳管平台，节点侧需要先备好解析与镜像仓库配置。

前置条件

  • 主机名、IP、网关、网段规划已经确认，并和其它节点不冲突。
  • 操作系统版本、内核参数、容器运行时要与存量节点保持一致，混版本最容易在后期踩坑。
  • 时间同步可用。时间偏差到分钟级，加入集群时会直接因证书校验失败而被拒绝。
  • 节点到镜像仓库、到集群 API Server、到纳管平台的网络均已放通，安全组与防火墙策略提前申请。
  • 有带外管理或串口可用。改网络和容器引擎配置时可能失联，别只靠 SSH。

核心配置项与原理

节点初始化真正要解决的问题只有三个：机器能不能稳定解析域名、能不能从私有仓库拉镜像、能不能被集群和纳管平台识别。前两项是基础，第三项依赖前两项。

DNS 配置有个容易被忽略的细节：/etc/resolv.conf 在部分系统上会被 DHCP 客户端或云初始化程序回写，节点重启后配置被覆盖，表现为「刚配好能用，重启就解析失败」。做法是把文件加不可变属性锁住，代价是后续要改 DNS 必须先解锁。

镜像仓库的配置方式取决于容器运行时的版本：较新的集群统一用 containerd，通过配置文件的 mirrors 与 configs 段落指定镜像加速和跳过证书校验；早期集群用 docker，写在 daemon.json 的 insecure-registries 里。两套写法不通用，先确认节点上的运行时类型再动手。

托管集群在 1.30 之后有个变化：集群内部组件交互改为走 API Server 的域名，而不是固定 IP。此时如果节点上解析不到这个域名，节点能 ping 通 IP 但加不进集群。该域名的解析记录通常保存在云侧的私有解析区域，与自建 DNS 的区不互通，需要单独添加。

操作步骤

  1. 系统基线。核对主机名、时区、时间同步、内核参数与存量节点一致，容器运行时已安装并设为开机自启。
hostnamectl set-hostname node-01
timedatectl set-timezone Asia/Shanghai
systemctl enable --now chronyd
  1. 配置 DNS 并锁文件，防止重启后被覆盖：
cat /etc/resolv.conf
# 写入统一 DNS 地址，例如 nameserver 192.0.2.53
lsattr /etc/resolv.conf
chattr +i /etc/resolv.conf

改完再执行一次 lsattr，属性里出现 i 才算生效。以后需要调整 DNS，先 chattr -i 解锁，改完再锁回去。

  1. 补充域名解析。若集群或纳管平台通过域名访问，把要用的几条记录一次性写进 /etc/hosts，避免后续按板块切换时反复改：
cat >> /etc/hosts <<'EOF'
192.0.2.10  console-a.example.com
192.0.2.11  console-b.example.com
192.0.2.12  registry-a.example.com
EOF
  1. 配置私有镜像仓库。containerd 场景编辑 /etc/containerd/config.toml：
[plugins."io.containerd.grpc.v1.cri".registry]
  [plugins."io.containerd.grpc.v1.cri".registry.mirrors]
    [plugins."io.containerd.grpc.v1.cri".registry.mirrors."registry-a.example.com"]
      endpoint = ["http://registry-a.example.com:80"]
  [plugins."io.containerd.grpc.v1.cri".registry.configs]
    [plugins."io.containerd.grpc.v1.cri".registry.configs."registry-a.example.com".tls]
      insecure_skip_verify = true

私有仓库需要认证时，在对应 configs 段落下再补一个认证子段，账号与口令从企业凭据系统取用后写入，配置文件的权限设为 600，不要提交到配置仓库。改完重启运行时：

systemctl restart containerd
systemctl enable containerd
crictl pull registry-a.example.com/library/pause:3.9

docker 场景编辑 /etc/docker/daemon.json：

{
  "insecure-registries": ["http://registry-a.example.com", "https://registry-a.example.com"],
  "registry-mirrors": ["http://registry-a.example.com"]
}
systemctl restart docker
docker pull registry-a.example.com/library/busybox:latest
  1. 托管集群在 1.30 以上版本，补 API Server 域名解析。域名由「apiserver + 集群专属域名后缀」拼成，解析目标是对应的负载均衡实例地址：
getent hosts apiserver.<cluster-id>.example.com
# 期望返回 192.0.2.10 这类集群入口地址

缺失时到云侧私有解析区域补一条 A 记录，不要试图在自建 DNS 上补，两边不互通。

  1. 预拉纳管平台 agent 镜像。仅当节点需要从公网或跨网段到平台侧拉取时才必做，纯内网集群由平台侧统一推送。用 crictl pull 或 docker pull 先拉一遍，避免纳管过程中因拉镜像超时反复重试。

  2. 加入集群或在平台上纳管。按集群既有方式执行 join 或由平台下发纳管指令，加入后给节点打好业务标签，必要时处理污点，保证调度落到预期的资源池。

验证

# 解析是否生效
getent hosts console-a.example.com
getent hosts apiserver.<cluster-id>.example.com

# 仓库是否可达
curl -sI http://registry-a.example.com/v2/

# 拉起测试镜像
crictl pull registry-a.example.com/library/pause:3.9

# 节点是否就绪
kubectl get nodes -o wide
kubectl describe node node-01
  • 节点状态为 Ready，且节点上纳管组件的 Pod 处于 Running。
  • 纳管平台侧能看到该节点，状态正常，没有一直转圈的同步中。
  • 重启一次节点，复查 /etc/resolv.conf 内容与文件属性，确认没有被回写覆盖。

风险与回滚

  • chattr +i 会让 DHCP、云助手、某些初始化脚本无法修改 DNS。上线前把原始内容记下来；需要恢复时先 chattr -i /etc/resolv.conf。
  • 修改容器运行时配置必然重启运行时，节点上已有的容器会被重启。先把节点置为不可调度并驱逐负载，再操作。
  • 加入集群失败不要反复重试 join，残留的 kubelet 配置会让后续加入一直报错。先清理 /etc/kubernetes 下的残留配置与 /var/lib/kubelet，再重新执行。
  • 主机名或 IP 与存量节点冲突，会导致节点注册覆盖或网络不可达。接入前用 kubectl get nodes -o wide 核对一遍。
  • 回滚思路：把节点从集群下线，驱逐负载，删除节点对象，然后恢复运行时与 DNS 配置，重新走一遍初始化流程。

常见问题

现象常见原因处理思路
重启后解析失效resolv.conf 被回写覆盖加不可变属性，重启后再验证
拉镜像报证书错误私有仓库用自签证书且未跳过校验补 tls 段落并重启运行时
拉镜像提示未授权仓库认证子段缺失或凭据过期补认证信息，权限设 600
节点 Ready 但加不进集群API Server 域名解析缺失在私有解析区域补记录，getent 验证
纳管组件一直重启agent 镜像没拉到或平台地址不通先手动 pull，再检查网络策略
join 反复失败上一次 join 残留配置清理残留后重新加入，不要盲目重试
