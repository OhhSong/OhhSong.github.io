大文件跨环境传输应急指引

借独立备份网卡与静态路由分离拷贝流量，应急传输大文件的现场操作路径。

2025年5月7日 5 分钟阅读 运维手册 传输应急网络 网络与传输

一句话定位

当同一虚拟化集群内的两台虚机需要互拷几十上百 GB 的文件，而业务网卡的带宽又撑不住时，用一块独立的备份网卡加一条静态路由，把拷贝流量从业务链路上摘出去。这份指引记录的就是这套应急做法的完整现场步骤。

适用场景

  • 数据库全量备份、镜像文件、日志归档需要在两台虚机之间搬运，单次体量在几十 GB 以上。
  • 业务网卡带宽接近跑满，直接拷贝会把线上接口拖慢甚至拖出超时。
  • 同集群内跨主机拷贝时，虚拟化层内部转发不会绕行物理出口，加上备份网卡后基本可以跑满万兆。
  • 应急窗口很短，等不及走专线或对象存储中转。

原理

虚拟化平台允许一台虚机挂多块虚拟网卡，多块网卡可以分属不同网段。给两台虚机各挂一块新网卡，配到同一个备份网段里，再在操作系统内为对端网段写一条指向备份网关的静态路由，两机之间的拷贝流量就会自动走这块新网卡，业务网卡的流量因此不受影响。

这里有两个容易搞错的点。一是路由必须是主机路由或按网段精确匹配，写成默认路由会把业务流量也带偏。二是备份网段的网关地址是固定约定值，两台机器必须用同一个网关，否则路由能配上但走不通。

前置条件

  • 变更窗口已确认，业务方知晓本次操作。
  • 在虚拟化控制台为两台虚机各新增一块网卡，记录网卡设备名（如 ens224）与 MAC 地址。
  • 备份网段与网关已规划好，示例中统一用 192.0.2.0/24，网关 192.0.2.1。
  • 目标主机上已准备好接收目录，剩余空间大于待传文件体积。
  • Linux 侧确认 SSH 服务可用，Windows 侧确认文件共享与共享账号可用。
  • 有控制台或带外通道可用，防止网卡配置失误后把自己锁在系统外。

操作步骤

1. Linux 主机配置备份网卡

先用 ip link 确认新增网卡的设备名，再为它单独建一个配置文件。不要直接改业务网卡的配置。

ip link
cp /etc/sysconfig/network-scripts/ifcfg-ens224 /root/ifcfg-ens224.bak 2>/dev/null
vi /etc/sysconfig/network-scripts/ifcfg-ens224
TYPE=Ethernet
BOOTPROTO=static
NAME=ens224
DEVICE=ens224
ONBOOT=yes
IPADDR=192.0.2.10
PREFIX=24

2. 写入永久路由

路由写进独立的 route 文件，文件名与网卡名对应，重启网络后会保留。

echo "192.0.2.0/24 via 192.0.2.1 dev ens224" > /etc/sysconfig/network-scripts/route-ens224

3. 启用网卡并校验

ifdown ens224 && ifup ens224
ip -4 addr show ens224
ip route show
ping -I ens224 192.0.2.1 -c 3

若 ifup 后地址没起来，先看 /var/log/messages 里的报错，多数是配置文件里 NAME 与 DEVICE 不一致，或备份网段与已有网段冲突。

4. Windows 主机配置

在网卡属性里把新增网卡的地址静态配成备份网段地址，掩码与前缀一致，然后加一条永久路由。-p 表示持久化，重启后依然存在。

route add 192.0.2.0 mask 255.255.255.0 192.0.2.1 -p
route print

随后把待接收的目录设置为共享，共享账号只给本次操作用的临时账号，用完立即回收。

5. 传输

Linux 之间首选 rsync，支持断点续传，中断后重跑即可接着传；单次小文件用 scp 更省事。示例中的端口按实际加固后的 SSH 端口填写。

# 断点续传，并限制带宽避免打满备份链路
rsync -avP --partial --bwlimit=300M /data/dump.tar.gz admin@192.0.2.11::backup/

# 单文件直传
scp -P 42222 /data/dump.tar.gz admin@192.0.2.11:/data/backup/

Windows 到 Windows 直接走共享目录映射后用资源管理器或 robocopy 拷贝；Windows 与 Linux 混传时，在 Linux 侧挂载共享或用 smbclient 取文件。

6. 校验

拷完必须比对校验和，体积一致不等于内容一致。

sha256sum /data/dump.tar.gz
# 在对端执行同一条命令，两处摘要一致才算完成

验证

  • ip route get 192.0.2.11 的输出里 dev 应为备份网卡，说明选路正确。
  • sar -n DEV 2 5 观察两块网卡的流量：备份网卡接近线速，业务网卡流量无明显抬升。
  • 传输过程中抽查业务接口响应时间，确认没有被拷贝流量拖慢。
  • 校验和一致，文件大小一致。
  • 操作完成后在业务侧再确认一次，相关服务无异常告警。

风险与回滚

网卡配置写错导致失联。 只在新增网卡上做配置，不动业务网卡；一旦失联，从控制台远程连接进入系统把错误文件改名后重启网络。

路由写宽了影响业务。 路由必须是备份网段的精确前缀，禁止写默认路由。发现业务异常时删掉 route 文件并执行 ifdown/ifup 还原。

带宽争抢。 拷贝流量虽在备份链路，但磁盘 IO 与 CPU 仍是共享资源，用 --bwlimit 限速并避开业务高峰。

磁盘写满。 传输前确认剩余空间，中途可用 df -h 观察；写满会影响同机的日志与数据库。

文件被覆盖。 rsync 默认会覆盖同名文件，追加 --ignore-existing 或在目标目录使用带时间戳的独立子目录。

回滚顺序固定为：停传输进程、删路由文件、还原网卡配置、重启网络、复核业务网卡与路由表。

常见问题

网卡起来了但 ping 不通对端。 检查两台机器是否在同一备份网段、网关是否一致、虚拟化侧两块网卡是否接在同一个虚拟交换机上。

路由表里有记录但流量还是走业务网卡。 用 ip route get 看实际选路，多半是存在更精确的旧路由或策略路由覆盖了配置。

ifup 报“设备未找到”。 虚拟化侧网卡没有正确挂载，或设备名写错；回到控制台核对网卡列表。

传输速度只有几百兆。 检查是否被限速参数限制、对端磁盘是否成为瓶颈、虚拟交换机链路是否出现丢包。

Windows 重启后路由消失。 添加路由时漏了 -p 参数，重新执行并确认 route print 中显示为持久路由。
